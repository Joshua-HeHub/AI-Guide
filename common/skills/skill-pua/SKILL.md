# 卡壳升级处理

## 何时使用

- 同一个方向已经失败 2 次以上，只是在改参数、改措辞、改格式，没有本质变化。
- 准备说“我解决不了”“请用户手动操作”“可能是环境问题”，但还没有做充分验证。
- 修完表面问题就想结束，没有做验证、回归、同类问题排查。
- 用户已经明确不满意，例如“再试试”“换个方法”“为什么还不行”。

## 核心原则

1. 穷尽方案前，不要轻易放弃。
2. 先查后问。提问前先用工具完成能做的排查。
3. 端到端交付，不只回答问题，还要验证结果。

## 升级流程

### L1：停止原地打转

满足以下任一情况就进入 L1：

- 同类失败重复出现。
- 只是在微调同一路径。
- 没有产生任何新信息。

此时必须：

1. 列出已经试过的方法。
2. 说明这些方法的共同问题。
3. 切换到一个本质不同的新方案。

### L2：拉高视角排查

如果 L1 后仍失败，按顺序执行下面 5 步：

1. 逐字读失败信号：报错、空结果、用户不满点、异常返回。
2. 主动搜索：搜索完整报错、官方文档、相关 issue、相似实现。
3. 读原始材料：读源码上下文、配置文件、接口文档、真实输入数据。
4. 验证前置假设：版本、路径、权限、依赖、配置、边界条件。
5. 反转假设：假设问题不在当前怀疑点，从反方向再查。

在前 4 步完成前，不要直接向用户追问笼统问题。

### L3：强制 7 项检查

如果 L2 后仍失败，必须逐项完成：

1. 读完失败信号全文。
2. 搜索核心问题。
3. 读失败位置周边原始上下文。
4. 用命令验证环境与前提条件。
5. 试一次对立假设。
6. 做最小隔离或最小复现。
7. 换工具、换方法、换技术路线，而不是只换参数。

## 主动出击清单

完成修复或实现后，至少自检这些问题：

- 我真的跑过验证吗？
- 改了代码后，是否做了 build、test、curl、实际运行或等价验证？
- 同文件、同模块、同模式下是否还有类似问题？
- 上下游依赖是否会被影响？
- 是否还有明显边界条件没有覆盖？

## 文件修改闭环原则

任何文件修改 = **修改动作 + 立即读出目标行（含行号和上下文）+ 两者对得上才算完成**。

- 不看到目标内容，不宣布"成功"
- exit code 0 不等于内容已写入（`sed` 不匹配时也返回 0）
- 验证时必须确认：行号在预期位置附近 + 上下文是目标位置

### sudo 文件修改标准流程

**禁止** `sudo sed -i`（转义复杂、静默失败、难验证）

```bash
cp <target> /tmp/xxx_tmp        # 1. 复制到 /tmp（无需 sudo）
# 在 /tmp/xxx_tmp 上做修改     # 2. 修改（sed/vim/任意工具）
grep -n "目标内容" /tmp/xxx_tmp # 3. 验证 /tmp 副本内容正确
sudo cp /tmp/xxx_tmp <target>   # 4. sudo cp 写回
grep -n "目标内容" <target>     # 5. 再次验证原位置
```

## 允许退出的条件

只有在完成充分排查后，才允许输出结构化失败报告。报告至少包括：

1. 已验证的事实。
2. 已排除的可能性。
3. 缩小后的问题范围。
4. 下一步最值得尝试的方向。
5. 交接所需的关键上下文。

## 输出要求

- 语气保持专业、直接、建设性。
- 不要输出羞辱、威胁、PUA 式人身攻击或施压话术。
- 如果需要向用户提问，必须先说明已查到的证据，再说明还缺什么信息。
- 如果声称“已完成”或“已修复”，必须附带验证证据。

## 禁止凭印象断言运行时行为

对任何涉及"某个组件/脚本会不会自动恢复/重试/继续运行"的问题，适用以下规则：

1. **必须先读代码或查日志验证**，不能凭印象或文档描述给出确定性结论。
2. 若来不及立即验证，必须用 `vscode_askQuestions` 明确告知用户："我尚未核实 X 的实际行为，建议你先手动确认，同时我去读代码验证。"
3. 不允许输出"会自动恢复""有重试逻辑""不需要手动干预"等断言，除非已通过代码阅读或实测确认。

**典型触发场景**：BMC 刷机/重启后问"压测会不会自动继续"——必须读 `run.sh` 错误处理分支后再回答，不能凭 monitor 脚本有重试逻辑就推断 run.sh 也会自动恢复。

## 适用范围

- 代码修复
- 调试排障
- 配置和部署
- API 集成
- 文档与研究
- 任何出现“重复失败、猜测、被动等待、未经验证就下结论”的场景
