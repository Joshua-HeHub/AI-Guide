# 代码审查反馈指南

## 表达原则

- 先说问题，再说原因，再说影响，最后给建议。
- 专注于代码和行为，不评价作者本人。
- 有证据时说结论，证据不足时说假设和风险，不要混在一起。
- 能给出触发条件时，要写清楚什么情况下会出问题。

## 推荐写法

- `这里有一个功能性回归风险，因为 ...，在 ... 条件下会导致 ...。`
- `这段逻辑当前依赖一个隐式前提：...；如果前提不成立，结果会变成 ...。`
- `这里建议补一条回归测试，覆盖 ... 场景，否则后续修改很容易再次引入同类问题。`
- `如果这里的调用失败，当前实现没有回滚或清理，可能留下 ... 状态。`

## 避免写法

- `这里不太好。`
- `感觉有问题。`
- `建议优化一下。`
- `写得太差了。`

## 反馈排序

- 先列高风险问题，再列中风险问题，最后才是低优先级建议。
- 一个问题如果已经足够阻塞合入，不要把大量样式建议堆在它前面。
- 如果没有明确问题，就直接说未发现明确问题，并补充验证边界和测试缺口。

## 缺口说明

- 只有片段，没有完整 diff 时，要写明审查覆盖范围有限。
- 只有代码，没有运行方式或需求背景时，要把不确定项单列出来。
- 看到潜在问题但证据还不足时，优先写成 `Open questions / assumptions`，不要强行定性。
