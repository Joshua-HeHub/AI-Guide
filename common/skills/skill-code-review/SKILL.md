# 结构化代码审查

## 使用条件

- 适用于审查 PR、MR、patch、commit 范围、单文件或单函数。
- 优先基于真实改动范围做审查；若只有代码片段没有上下文，要明确说明结论覆盖范围有限。
- 优先发现功能正确性、行为回归、安全风险、边界条件和测试缺口，不要先陷入样式问题。
- 需要展开检查点时，参考 `resources/REVIEW-CHECKLIST.md`；需要组织反馈语气和表达方式时，参考 `resources/FEEDBACK-GUIDELINES.md`。
- 当用户提供 Gerrit MR/Change 链接或只给 change number、且需要读取真实 diff 时，才按需读取 `resources/GERRIT-DIFF-FETCH.md`；普通代码审查不要加载或执行该流程。

## 按需资源

- `resources/REVIEW-CHECKLIST.md`：需要展开完整检查清单时加载。
- `resources/FEEDBACK-GUIDELINES.md`：需要组织评审语气和反馈表达时加载。
- `resources/GERRIT-DIFF-FETCH.md`：仅在需要从 Gerrit MR/Change 拉取真实 diff 时加载；不要用网页抽取 diff 代替 Gerrit SSH/Git ref。

## 审查步骤

1. 先确认上下文：改了什么、为什么改、影响哪些模块、是否有测试或验证路径。
2. 优先审查高风险项：功能正确性、状态机/并发、内存或资源生命周期、权限边界、输入校验、兼容性。
3. 再检查中风险项：错误处理、日志、可维护性、性能、配置影响、测试覆盖。
4. 最后再看低风险项：命名、注释、局部可读性、文档一致性。
5. 任何结论都尽量落到具体文件、函数、条件分支、输入场景或调用链，不要只给抽象评价。

## 输出要求

- 如果用户是在“review”语境下提问，默认先给 findings，再给问题或假设，最后给简短总结。
- findings 只写真正有价值的问题：Bug、风险、回归、缺失测试、错误假设、脆弱实现。
- 每条 finding 必须说明：问题是什么、为什么成立、可能影响什么、在什么条件下触发。
- 能定位时要带文件和函数；无法精确定位时要明确说明依据来自哪段逻辑。
- 如果没有发现明确问题，要直接说“未发现明确问题”，并补充剩余风险或未验证项。

## 严重度建议

- 高：会导致功能错误、崩溃、数据损坏、安全问题、明显回归，或修复前不应合入。
- 中：当前未必立即出错，但存在高概率维护风险、边界缺陷、测试缺口或行为不一致。
- 低：不影响当前正确性，但会增加理解成本、误用概率或后续修改成本。

- 确认问题与待确认风险分开输出。SPX report 严重度使用 `[CRITICAL]`、`[MAJOR]`、`[MINOR]`、`[NIT]`；每条确认问题写出代码位置、触发条件、风险后果、修复建议和验证建议。待确认项写缺失材料及关闭条件，不伪装成已确认 Bug。
- 报告包含审查提交或未提交 diff 范围、变更意图、各严重度问题数量、测试证据、自查评估表、已知配置风险及实际执行的检查。结论与 findings 优先；不能虚构独立复核者、置信度、实测或构建结果。
- 测试覆盖修改点及相关功能；硬件或配置改动按受影响组合评估，明确保留配置升级、状态恢复和北向接口的验证缺口。必要时参考 SIT 用例，未知套餐或硬件组合先记录待确认。
- AI Review report 需要记录到对应 Redmine，且每条 Review 问题都需澄清：确认并修复、非问题及证据，或待确认及关闭条件。只输出可写入内容；用户未授权时不要自动发布评论。
- 飞书文档里的传感器去抖 report 是示例，不是本次审查证据。不得照搬示例问题或只按传感器名称断言阈值、事件掩码和去抖语义。

## 审查重点

- 功能是否与需求一致，是否遗漏关键路径。
- 修改是否破坏原有调用方、协议、配置或向后兼容性。
- 错误路径、超时、空值、异常输入、重复调用、并发场景是否成立。
- 安全边界是否变化：认证、授权、输入校验、命令执行、路径访问、敏感信息处理。
- 资源是否正确释放，状态是否会泄漏，是否会引入竞态或重入问题。
- 测试是否覆盖主路径、失败路径和回归点；若缺失，要点明最需要补的测试。

## 审核清单

以下为结构化审查时的核对清单（逐项确认）：

1. 检查提交（commit）标题和描述是否合理。
2. 检查提交的代码是否符合编码规范；对新增或改动的函数，补充使用说明、参数说明和返回值说明；对改动的模块，增加必要注释说明。
3. 检查全局变量或宏的定义是否会与原代码中的定义冲突。
4. 检查有文件操作的代码是否都有打开和关闭（包含正常返回和异常返回路径）。
5. 检查有内存申请的代码是否都有释放（包含正常返回和异常返回）；对第三方库（如 cjson）使用要重点关注。
6. 检查有加锁的代码是否都有解锁（包含正常返回和异常返回），禁止锁拷贝（lock copy）。
7. 检查函数命名或 log 打印是否与实际功能相符；注意函数命名错别字或打印日志不合理；SPX 新增自有函数按实际项目使用 `Byte`（字节）或 `IEC`（IEC OTS）前缀，并核对声明、定义和调用。
8. 检查 if 等判断语句的判断条件是否合理。
9. 检查循环语句的退出条件是否合理。
10. 检查数组的操作是否可能越界。
11. 检查内存的 copy（如 memcpy/strncpy 等）是否可能越界或未校验长度。
12. 检查当前 BMC 分区大小和位置是否改变（没有改变则为 PASS）。
13. 检查当前改动使用保留配置的方式升级后是否可以生效。
14. 检查是否有日志不能正常转储，导致 BMC 内存泄漏的问题。
15. 涉及硬件操作或配置的改动是否会影响到其他配置；任何对硬件的控制，需附带测试或测量结果（北向 IPMI、WEB、Redfish 接口）。
16. 若提交代码包含 sensor 类型，检查其阈值设定是否合理（需 EE/Power/Thermal 部门确认邮件）；明确 sensor number、sensor type、event assert/deassert mask 等字段的修改点及预期结果。
17. ADC sensor AC 5 次读值浮动是否超过 3%。
18. 检查硬件访问是否有检查返回值并进行异常处理。
19. 检查 snprintf 和 printf 传入的字符串参数是否为带格式的字符串，避免 format string 漏洞或传入非格式串。
20. 对已有函数修改逻辑时，遍历排查该函数所有上下级调用处，并逐一评估改动逻辑对原流程的影响是否都在预期内。
21. 共享资源（全局变量/共享内存等）是否存在跨线程使用；跨线程使用时，评估其他写操作对所有读操作是否有影响并加锁或同步保护。
22. 变量或结构体是否有初始化；循环逻辑中每一圈结构体是否有必要的 memset（常见于字符串未清空）。
23. 检查 AC Cycle 操作对当前功能设计是否有影响，评估断电重启后的初始化、状态恢复和相关功能；没有实际测试时记录验证缺口。

## 固定输出模板

优先使用以下结构：

1. `Findings`
2. `Open questions / assumptions`
3. `Brief summary`

写 `Findings` 时，按严重度从高到低排序。单条 finding 推荐格式：

- `[高/中/低] 文件或模块：一句话结论`；SPX report 改用上方 `[CRITICAL/MAJOR/MINOR/NIT]` 严重度。
- `原因：...`
- `影响：...`
- `触发条件：...`
- `建议：...`

## 约束

- 不要把纯样式偏好伪装成严重问题。
- 不要为了凑数量而输出低价值意见。
- 不要在证据不足时下过度确定的结论；缺口要直接写出来。
- 若用户明确要求“review”，主回答应以问题发现为主，而不是先做改法设计。
- 若用户给出 diff 或改动范围，优先围绕变更本身审查，不要无边界地扩散到整个仓库。
