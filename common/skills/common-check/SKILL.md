# Common Check

目标：把问题从来源项目追到目标分支和目标机台，分别给出证据，不因同源代码直接宣称跨项目复现。

定位项目、仓库或机台时，先读 [项目与机台索引](./references/projects-and-machines.md)。普通单点分析不必加载全部专项技能。

## 工作流程

### 1. 固定排查对象

记录来源项目、现象与预期、目标项目、任务范围。区分“比较源码”“修改代码”“核查镜像”“实机验证”。

- 以用户问题、源码入口或失败日志为起点，选择直接决定行为的函数。
- 多项目任务逐项列出目标；从其他项目反查本项目时执行相同流程。
- “32 66”这类裸数字可能是协议命令或机台简称。先确认含义，不自行解释成 IP 或刷机要求。

完成条件：能明确说出本轮查哪个行为、哪些项目，以及允许做到哪一层。

### 2. 固定源码基线

- 按索引解析仓库和分支；项目名可能是共享仓库的分支，不是独立目录或仓库。
- 核对远端提交与本地对象；用 `git show`、`git grep` 比较不可变提交，默认不切换工作分支。
- 本地缺对象时可获取目标 Git 对象；这会写对象库，不等于允许更改工作树、提交或推送。
- 查看相关项目配置、覆盖包及生成规则；候选工作树存在不证明其分支正确。
- 仅读取问题所需的邻近实现。图谱存在时可辅助定位，最终以对应提交的源码验证。

完成条件：每个项目都有仓库、分支、提交号、相关配置入口；旧快照明确标注日期。

### 3. 做有区分度的源码比较

对每个目标项目核实以下链路，而非仅比较同名文件或包版本：

1. 入口如何产生参数或保留位图。
2. 拥有该行为的实现如何计算、迁移或重置配置。
3. 项目开关、覆盖包、安装脚本是否改变实际路径。
4. 默认值来自代码兜底、模板、生成配置还是运行态持久化。

先形成一个可证伪的局部假设，再选最便宜的区分检查。预置值等于默认值的实验不能证明“恢复默认”；应选择合法非默认值比较前后。

完成条件：每个目标均能解释为何受影响或不受影响；链路未闭环的项目标为“待确认”。

### 4. 按需确认镜像或实机

**镜像层**：绑定项目、配置、版本和校验值，检查实际生成或打包内容。源码模板、版本字符串和文件名均不能单独证明镜像内容。

**实机层**：仅在任务包含实机检查且已确认目标后连接。按以下顺序推进：

1. 确认 BMC、Host、串口服务器角色，以及机台身份、当前版本、启动 bank 和占用情况。
2. 采集与假设相关的只读基线；记录运行配置和镜像默认配置，避免只拍页面。
3. 提出最小实验，明确预置值、操作、预期、证据和可能影响。
4. 涉及状态变更时取得该操作的明确授权，再执行一次并验证结果。
5. 报告最终版本、配置和未恢复项；恢复操作本身也必须在授权范围内。

机台、版本或镜像不匹配时停止状态变更，先澄清。不用历史 IP、ping 成功或同型号硬件替代身份核实。

完成条件：实验前后证据对应同一机台和本轮操作；仅接口成功不算刷写、重置或故障复现成功。

### 5. 分层给出结论

| 证据层级 | 可以说明 | 不能直接说明 |
|---|---|---|
| 源码确认 | 指定提交存在相同控制路径或缺口 | 已发布镜像必然包含它、目标机已复现 |
| 镜像确认 | 指定校验值的产物包含相关实现或默认配置 | 目标机实际启动了该镜像、运行配置已生效 |
| 实机确认 | 指定机台和版本在本轮操作中的实际行为 | 其他项目、其他版本及 SIT 原始操作的历史原因 |

输出每个项目的分支/提交、结论、证据层级与剩余缺口。记录证据日期及必要的代码位置、日志路径。

“代码目前如此”不等于符合规格。界面承诺、产品规格与实现不一致时，明确指出差异；无原始过程证据时，不断言测试人员预置错误或截图时序有误。

## 状态变更边界

- “可以调试”或“继续分析”不是刷机许可；分别确认目标 IP/机台身份、目标版本/镜像、操作方式、配置保留模式和重启影响。
- 升级、降级、同版本重刷、不保留配置、清日志、重启及电源操作都可能改变现场，执行前说明影响并取得授权。
- 恢复出厂必须先请示。不得用不保留配置刷机绕过清配置确认，也不因缺少同版本镜像擅自选择旧版。
- 用户要求暂停或先不动时，保留现场；不以“收尾”或“恢复原状”为由追加刷机、清配置。
- 对共享设备一次只允许一个执行者发出状态变更；其他并行工作保持只读。
- 凭据留在既有安全存储中，不写入 skill、报告或命令日志。秘密输入由用户直接在终端完成。
- 不自动构建；需要编译时先获得明确要求，并核实 License 与构建环境。
