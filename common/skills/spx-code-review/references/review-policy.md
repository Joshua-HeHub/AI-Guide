# BMC 代码审查策略

## 平台假设

- Aspeed AST2500/AST2600/AST2700，ARM 架构。
- 嵌入式 Linux、非 systemd、资源受限。
- 多线程与多进程混合的长驻 daemon，按年级运行周期评估风险。
- 网络暴露面包括 IPMI、Web、Redfish、IPv4 和 IPv6。
- 主要语言为 C，辅助语言为 Python、Shell、DTS 和 DTSI。

默认按生产级 BMC 固件审查，不做基础语法教学，不使用情绪化表达。

## 基本规则

- 问题位置使用 diff 右侧的新版本行号。
- 单行问题提供同一个起止行号，多行问题提供起止范围。
- 每个问题必须引用对应代码并说明后果和具体修复方式。
- 主观改进使用建议或提问，不因个人风格偏好阻塞合入。
- 相同根因的问题合并，避免重复报告。
- 未发现问题时简洁输出“未发现问题”，并列出已执行的检查和未覆盖的验证范围。

## 审查优先级

严格按以下顺序检查，高优先级未完成前不得跳到低优先级：

1. 内存安全
2. 线程安全与进程安全
3. 资源释放完整性
4. 边界检查
5. 错误路径处理
6. 安全性
7. 命名与规范

## 严重级别

| 级别 | 标签 | 定义 | 阻塞合入 |
|---|---|---|---|
| 致命 | `[CRITICAL]` | 安全漏洞、数据丢失、生产 crash | 是 |
| 重大 | `[MAJOR]` | Bug、逻辑错误、显著性能回退 | 是 |
| 次要 | `[MINOR]` | 改善性修改、降低维护风险 | 否 |
| 琐碎 | `[NIT]` | 命名、格式或低风险清理 | 否 |

## 审查约束

1. 输出语言与用户输入语言一致。
2. 完整检查审查范围，但只报告有代码证据支持的问题。
3. 默认不直接修改代码，只有用户明确选择修复后才进入修改流程。
4. 优先审查 `.c`、`.h`、`.py`、`.sh`、`.dts` 和 `.dtsi`；文档和纯配置仅在用户指定或与变更行为直接相关时审查。
5. 用户提及的相关模块、调用链和设计上下文必须纳入判断。
6. Commit、PR 或 MR 审查必须读取标题、Description、测试步骤、测试结果和 Tracker；尝试获取后仍无法取得时，在 Review 事项汇总相应行标记为“当前项有风险”、填 `X` 并关联 `风险确认 #N`，说明缺失信息，不将材料缺口误报为代码缺陷。仅文件审查不涉及提交信息时标记为“已检查-不涉及”、填 `V` 并关联 `—`。概览中的“待提供”或“未检查”只表示证据进度，不得代替汇总表的三态和 `V`/`X` 标记。
7. 新增或修改全局变量、全局数组、`extern` 符号或宏时，必须执行全仓符号冲突搜索。
8. Review 事项汇总的输出范围、三态结果、`V`/`X` 标记与关联项填写规则以 `assets/review-report-template.md` 为准。专项强制提示必须关联 `风险确认 #N`，补齐材料或关闭普通风险不自动解除强制 `X`；材料齐全时如实记录已验证范围，不虚构缺口。

## 禁止事项

- 未读完审查范围就批准。
- 只因格式或个人偏好阻塞 PR。
- 输出没有严重级别、代码位置或原因的模糊代码问题；风险确认项按模板四要素说明，不虚构代码缺陷级别。
- 跳过安全检查、错误路径或资源清理检查。
- 要求与本次变更无关的重构。
- 批评作者或使用情绪化措辞。
- 把生产审查写成基础教学材料。
