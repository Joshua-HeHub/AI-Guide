# SPX Sensor 与 ADC 风险检查

## 触发条件

仅当 diff 涉及以下内容时加载本清单：

- Sensor 定义、阈值、事件处理或读值转换。
- `sensor number`、`sensor type`、`event assert mask`、`event deassert mask`。
- ADC 采样、转换、校准、滤波或 AC Cycle 读值逻辑。

未命中时将“Sensor 参数”和“ADC Sensor 测量”标记为 `已检查-不涉及`。

## Sensor 参数

- [ ] Sensor number 是否唯一并与 SDR/配置及北向接口一致？
- [ ] Sensor type、单位、线性化和读值范围是否与实际硬件一致？
- [ ] 上下阈值及 hysteresis 是否合理，assert/deassert 条件是否对称且不会抖动？
- [ ] `event assert mask` 和 `event deassert mask` 是否只启用预期事件？
- [ ] 修改点、预期结果和 EE、Power、Thermal 部门确认材料是否明确？

## Sensor 负值与有符号转换

每个新增或修改的 Sensor 都必须判断原始值或中间结果是否可能为负数，并沿完整数据链检查符号类型：

- [ ] 根据 Sensor 类型、硬件规格、读取 API、错误返回、校准偏移、比例换算和温度/电流等物理范围，判断负值是否为合法读值、错误码还是异常数据。
- [ ] 原始值、计算中间值、结构体字段、缓存、函数参数/返回值、阈值和北向编码类型是否正确使用有符号类型？
- [ ] 在赋值给 `unsigned`、较窄整数类型、位域或网络协议字段前，是否先显式检查负值和范围？禁止依赖隐式转换或直接强制转换。
- [ ] 乘除、偏移、线性化、平均、滤波和舍入过程中是否可能由非负原始值计算出负数？
- [ ] 负值是否在转换为无符号前参与阈值比较，导致被转换成超大正数并错误触发上限告警？
- [ ] API 用负数表示错误时，是否在数值换算和缓存前区分错误码与有效 Sensor 读值？
- [ ] 负值处理策略是否符合设计：保留合法负值、钳位到允许下限、标记 `No Reading` 或进入明确错误路径；不得一律钳位为 0 掩盖有效负温度或负电流。
- [ ] IPMI、Web、Redfish 对合法负值及无效负值的呈现是否一致，线性化/编码是否支持负数？
- [ ] 测试是否覆盖合法负值、`-1`/错误码、最小允许值、低于下限值、零值和负值转无符号边界？

发现任一可能的负值在未检查情况下流入无符号变量、阈值或北向编码时，标记为 `当前项有风险`。报告必须指出从负值来源到无符号赋值及错误告警的完整路径。

## Sensor 显示状态场景

每个新增或修改的 Sensor 都必须沿配置、初始化、采样、状态转换和北向呈现路径，分别确认以下场景：

- [ ] **Disabled** — 哪些产品配置、enable/disable 标志、硬件在位状态、功能开关或生命周期状态会使 Sensor 显示 `Disabled`？由哪个字段、返回码或状态位决定？
- [ ] **No Reading** — Sensor 已启用时，哪些初始化未完成、设备未就绪、读取失败、超时、数据无效、读值过期或依赖条件缺失会使其显示 `No Reading`？
- [ ] **告警值** — 哪些有效读值跨越阈值、离散事件置位或故障状态会显示告警值？必须说明阈值/事件条件、assert/deassert 规则及恢复条件。
- [ ] 当多个条件同时成立时，`Disabled`、`No Reading`、正常值和告警值的显示优先级是否明确并与 IPMI、Web、Redfish 一致？
- [ ] 状态恢复后是否会从 `Disabled`/`No Reading`/告警值正确回到正常读值，是否存在旧值或旧告警残留？

某类状态在设计上不可能出现时，也必须在报告中写明“无此场景”并引用代码、配置或协议依据，不能省略或凭推测填写。

## 温度 Sensor 散热策略联动

新增温度 Sensor 时，必须同步确认其是否纳入散热控制；不能只检查 Sensor 能否显示和告警：

- [ ] 使用 Sensor 名称、number、对象路径、配置键和读取接口全仓搜索 fan control、PID、thermal zone、风扇曲线、降频、功率限制、关机保护及平台策略中的引用。
- [ ] 是否新增或更新对应散热策略，并明确适用产品、硬件配置、电源状态和温控区域？
- [ ] 策略使用的 Sensor 标识、单位、比例、偏移和采样周期是否与新增 Sensor 一致？
- [ ] 正常、warning、critical 等温度区间分别触发什么动作，例如提高 PWM、切换风扇档位、限制功率、降频或保护关机？
- [ ] 策略触发阈值、回差和恢复条件是否与 Sensor 告警阈值协调，避免温度振荡、频繁切换或告警后不降温？
- [ ] Sensor 显示 `Disabled`、`No Reading`、读取超时、数据过期或超出物理范围时，是否进入明确的 fail-safe 散热策略，而不是按 0、旧值或正常温度处理？
- [ ] 多 Sensor 参与同一 thermal zone 时，最大值、平均值、权重、冗余和单点失效策略是否明确？
- [ ] 是否覆盖启动、AC Cycle、风扇故障、Sensor 恢复和高温持续场景的联动测试，并提供温度输入与风扇 PWM/转速或保护动作的对应结果？

如果新增温度 Sensor 仅用于监控、不参与散热控制，报告必须写明“无需新增散热策略”的设计依据和 EE/Power/Thermal 确认材料。没有对应散热策略、fail-safe 处理或设计确认时，标记为 `当前项有风险`。

## Sensor 告警与 Health LED 联动

每个新增或修改的 Sensor 都必须检查告警事件是否有配套 Health LED 映射，并在报告中逐项列出：

- [ ] 使用 Sensor 名称、number、event type、阈值事件、SEL/event handler 和 health aggregator 标识，全仓搜索 Health LED、system health、fault LED、front-panel LED 或平台指示灯策略中的引用。
- [ ] 每种 threshold 告警（如 LNC/LCR/LNR、UNC/UCR/UNR）和离散告警分别对应什么点灯级别、颜色、常亮/闪烁模式及 health severity？
- [ ] `Disabled`、`No Reading`、读取超时、数据无效和 Sensor 缺失是否影响 Health LED？不影响时是否有明确设计依据？
- [ ] `event assert mask`、`event deassert mask` 与 LED assert/deassert 规则是否一致，是否存在告警已上报但 LED 不亮或告警恢复后 LED 不灭？
- [ ] 多个 Sensor 或多个告警同时存在时，LED 是否按最高严重级别聚合，优先级和降级规则是否明确？
- [ ] 告警值跨回正常范围后，是否经过阈值回差、debounce 和有效读值确认再恢复 Health LED，避免抖动？
- [ ] Health LED 恢复是否要求该 Sensor 的事件 deassert、所有同级/更高级告警清除、锁存状态复位、人工确认或 AC Cycle？条件必须明确。
- [ ] Sensor 从 `No Reading`/`Disabled` 恢复时，旧告警和 LED 状态是否正确重算，避免残留或提前熄灭？
- [ ] IPMI SEL、Web/Redfish health 状态与实体 Health LED 的严重级别和恢复时机是否一致？
- [ ] 测试是否覆盖每种告警 assert、deassert、多告警叠加、严重级别升级/降级、读值恢复和 LED 恢复？

如果该 Sensor 按设计不影响 Health LED，报告必须写明“无 Health LED 联动”及平台策略或产品设计依据。缺少告警到 LED 级别的映射、聚合优先级或恢复条件时，标记为 `当前项有风险`。

## ADC 专项

- [ ] 原始 ADC 值到工程值的转换、比例、偏移、舍入和饱和处理是否正确？
- [ ] 采样次数、间隔、滤波和异常值处理是否符合设计？
- [ ] AC Cycle 后校准、参考电压和初始化顺序是否稳定？
- [ ] 是否提供 AC 场景连续 5 次原始读值与换算结果，并按项目约定确认浮动不超过 3%？

## 证据与报告

代码命中且检查无风险、材料完整时标记为 `已检查-无风险`。发现参数/测量风险或缺少材料时标记为 `当前项有风险`，并列出：

- 触发代码位置和变更字段。
- 预期读值、事件或阈值行为。
- 每个 Sensor 的 `Disabled`、`No Reading` 和告警值显示场景、判定依据、状态优先级及恢复条件。
- 每个 Sensor 是否可能为负数、负值来源、全链路有符号/无符号类型以及负值处理策略；存在风险时列出负值转换为超大正数并触发告警的路径。
- 新增温度 Sensor 对应的散热策略入口、thermal zone/PID/风扇曲线引用、触发阈值、控制动作、fail-safe、恢复条件和联动测试；仅监控时提供无需新增策略的设计依据。
- 每个 Sensor 的所有阈值/离散告警对应的 Health LED 级别、颜色/模式、并发告警优先级，以及 event deassert、回差、有效读值、锁存和其他告警清除后的恢复条件。
- 所需部门确认材料或连续五次测量数据。

任一 Sensor 缺少三类显示场景中的一项、状态优先级不明确，或无法从代码/配置确认时，必须标记为 `当前项有风险` 并列出待补充证据，不得标记为 `已检查-无风险`。

## 严重级别参考

- 错误阈值或事件掩码可导致保护失效、误关机或硬件损坏：`[CRITICAL]` 或 `[MAJOR]`。
- 未处理负值赋给无符号类型，导致超大读值、误告警或错误保护动作：`[MAJOR]`；可能造成硬件损坏或误关机时提升为 `[CRITICAL]`。
- 新增温度 Sensor 未接入必要散热策略，或 `No Reading`/超时未进入 fail-safe，可能导致过热或硬件损坏：`[CRITICAL]` 或 `[MAJOR]`。
- Sensor 告警缺少 Health LED 映射、严重级别错误或恢复条件不完整，导致故障不可见、误亮或告警恢复后不灭：`[MAJOR]`；掩盖关键硬件故障时可提升为 `[CRITICAL]`。
- Sensor 标识、转换或北向呈现错误：`[MAJOR]`。
- 仅缺少确认邮件或测量数据：使用提交者确认项，不虚构问题。
