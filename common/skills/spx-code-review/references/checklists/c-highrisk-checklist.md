# C 语言十大高风险错误 — 嵌入式专项检查

审查 BMC C 代码时, 必须逐类排查以下高风险错误模式。

---

## 1. 未定义行为 (Undefined Behavior)

UB 在 BMC 长驻进程中表现为偶现 crash、运行数小时后异常、极难复现。

- [ ] 变量未初始化直接使用
- [ ] 越界访问数组
- [ ] 空指针解引用
- [ ] 指针算术超出对象范围
- [ ] 修改字符串常量
- [ ] 多次修改同一变量且无序列点 (如 `a[i++] = i`)
- [ ] 移位操作超过类型宽度 (如 `1 << 33` 对 32-bit int)
- [ ] 带符号整数溢出
- [ ] 函数声明与实际定义不匹配
- [ ] 返回局部变量地址

## 2. 指针相关错误

```c
// 危险示例
malloc(sizeof(ptr));  // 应为 sizeof(*ptr) 或 sizeof(type)
```

- [ ] 野指针使用 (指向已释放或未分配的内存)
- [ ] 指针未初始化就直接解引用
- [ ] free() 后指针未置 NULL
- [ ] 多级指针分配层级是否匹配
- [ ] 指针类型强制转换是否合法
- [ ] void* 转换安全性
- [ ] sizeof(指针) 和 sizeof(类型) 是否混淆

## 3. 字符串处理错误

原则：**禁止无边界字符串操作**。

- [ ] strcpy — 是否存在目标缓冲区溢出风险？（→ 用 strlcpy）
- [ ] strcat — 是否存在溢出风险？（→ 用 strlcat）
- [ ] strncpy — 是否在末尾补了 '\0'？（strncpy 不保证 '\0'）
- [ ] snprintf — 返回值是否被检查？
- [ ] strlen — 目标字符串是否保证以 '\0' 结尾？
- [ ] sprintf — 是否仍在使用？（→ 用 snprintf）

## 4. 内存分配错误模式

```c
// 安全写法 — realloc 必须用临时变量
tmp = realloc(ptr, new_size);
if (!tmp) {
    // 处理失败, ptr 仍然有效
}
ptr = tmp;
```

- [ ] realloc — 是否用临时变量接收？（直接用原变量接收可能导致原内存泄漏）
- [ ] 分配大小 — 是否存在整数溢出（如 `malloc(n * size)` 中 n 来自外部）
- [ ] calloc — 参数顺序是否正确？（calloc(nmemb, size)）
- [ ] 循环内 malloc — 是否有对应的 free？是否累积增长？
- [ ] 内存碎片 — 频繁小块分配/释放是否有碎片风险？

## 5. 整数类型与隐式转换

```c
/* 风险示例：赋值时已经把 size_t 转换成 int。 */
int len = strlen(buf);
if (len < 0) {
    /* 并非永远为假，也不能可靠判断转换前的长度是否超出 int 范围。 */
}
```

`strlen` 返回 `size_t`，但赋值后的 `len` 已是有符号的 `int`。长度超过 `INT_MAX` 时，转换不能保证保留原值，不能依靠转换后的负值检查判断是否超范围。长度应优先保留为 `size_t`；仅当下游接口确实要求 `int` 时，才在转换前检查范围。

```c
#include <limits.h>
#include <stddef.h>

/* 调用方先用 size_t 接收 strlen 的结果，再按下游接口需要转换。 */
static int length_to_int(size_t length, int *out_length)
{
    if ((NULL == out_length) || (length > (size_t)INT_MAX)) {
        return -1;
    }

    *out_length = (int)length;
    return 0;
}
```

此示例仅说明标准库长度类型和转换边界，不改变项目编码规范的适用要求。

- [ ] 有符号与无符号比较 — 是否产生意外行为？
- [ ] size_t 与 int 混用 — size_t 是无符号的
- [ ] 长度转换 — 是否在转换为 `int` 等较窄类型前检查目标类型范围？
- [ ] 负值赋值给 unsigned — 是否会导致超大值？
- [ ] 循环变量类型 — 是否可能因类型不匹配导致死循环/提前退出？
- [ ] 整数乘法溢出 — 是否在分配大小或偏移计算中？

## 6. 结构体相关错误

网络协议相关结构体必须使用固定宽度整数类型。

- [ ] 结构体 padding — 是否影响网络协议或硬件寄存器的字节布局？
- [ ] 直接 memcpy 结构体到网络 — 是否考虑了字节序和对齐？
- [ ] 结构体未初始化 — 是否 memset 或逐字段初始化？
- [ ] 跨平台对齐 — 是否使用 `__attribute__((packed))` 控制？
- [ ] 位域 — 是否可跨平台/跨编译器移植？

## 7. 宏使用风险

```c
// 危险宏示例
#define MAX(a,b) a>b?a:b
// MAX(x++, y) 会多次求值 x++
```

- [ ] 宏参数是否加了括号？（`#define SQUARE(x) ((x)*(x))`）
- [ ] 宏是否有副作用风险？（参数在宏体内被多次求值）
- [ ] 多语句宏是否使用 `do { ... } while(0)` 包裹？
- [ ] 宏名是否全大写 + `_` 组成？

## 8. 错误的返回值处理

原则：**所有系统调用和库函数必须检查返回值**。

- [ ] 函数返回值被忽略 — 调用者未使用返回值
- [ ] read() / write() — 返回值是否被检查？（可能返回短读/短写）
- [ ] pthread_create() — 返回值是否检查？
- [ ] fclose() — 返回值是否检查？（flush 可能失败）
- [ ] malloc/calloc/realloc — 返回值是否检查 NULL？
- [ ] errno — 是否在使用前被覆盖？（在调用其他函数后检查）

## 9. 信号处理风险

原则：**信号处理函数必须极简**。

- [ ] 信号处理函数中是否使用了 printf？(非 async-signal-safe）
- [ ] 信号处理函数中是否使用了 malloc？(非 async-signal-safe）
- [ ] 是否修改了全局非原子变量？（可能产生竞争）
- [ ] 正确做法：只设置 `volatile sig_atomic_t` 标志, 主循环轮询

## 10. 长时间运行风险点

默认假设：该代码持续运行 1 年以上不中断。

- [ ] 计数器是否可能溢出？（如 32-bit 计数器每秒 +1, 约 136 年后溢出, 但高频计数器有风险）
- [ ] 内存是否累积增长？（即使每次只泄漏 1 字节, 年级运行也会撑爆）
- [ ] 日志是否无限增长？（是否做了轮转/限制？）
- [ ] 队列长度是否有限制？（无上限队列会在异常流量下撑爆内存）
- [ ] 线程/进程创建是否有限制？（是否根据请求动态创建且无上限？）
- [ ] 定时器/timerfd 是否正确释放？
- [ ] epoll/socket 描述符是否正确关闭？
