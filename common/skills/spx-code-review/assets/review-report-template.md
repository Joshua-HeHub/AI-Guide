# 代码审查报告

## 审查概览

- 审查文件：
- 审查范围：
- 推断意图：
- 问题统计：`[CRITICAL] x 0`、`[MAJOR] x 0`、`[MINOR] x 0`、`[NIT] x 0`
- 提交标题：
- 提交类型：Bug 修复 / 新功能或功能修改 / 未知
- Tracker：
- 测试证据：已提供 / 部分提供 / 待提供 / 未检查

“测试证据”只表示材料与检查进度，不是 Review 事项汇总的状态枚举。Commit、PR 或 MR 所需信息在尝试获取后仍无法取得时，相应汇总行必须填写“当前项有风险”、标记 `X` 并关联 `风险确认 #N`，列出缺失材料；不得仅以“待提供”或“未检查”代替风险标记。

## 变更可视化

根据 `references/workflows/mermaid-guidelines.md` 同时输出“变更前方案”和“变更后方案”两张对照图；仅注释或格式变更可省略。两张图必须使用相同图类型、方向和可比较的节点名称。

### 变更前方案

基于 diff 左侧或目标分支基线代码绘制。无法取得基线代码时，不得猜测，应明确写明“变更前方案待提供基线代码”。

```mermaid
flowchart LR
    A[原入口] --> B[原处理]
    B --> C[原结果]
```

### 变更后方案

基于 diff 右侧或当前变更代码绘制，并高亮新增、修改或删除后的关键路径。

```mermaid
flowchart LR
    A[原入口] --> B[变更后处理]
    B --> C[变更后结果]
```

## Review 事项汇总

固定输出下表全部检查领域，不得省略任何一行。状态只能使用：

- `已检查-不涉及`：本次变更未涉及该领域，并在结果中简述判断依据。
- `已检查-无风险`：本次变更涉及该领域，已完成检查且未发现风险或证据缺口，且未命中专项强制提示条件，并说明检查范围或证据。
- `当前项有风险`：发现确定性问题、潜在影响、缺少必要证据，或命中专项强制提示条件；必须按**四要素**说明：代码位置、判定依据、可能后果、实际缺失材料（如有）。本报告所有风险说明统一使用四要素。

“标记”列必须填写且只能使用：

- `V`：状态为 `已检查-不涉及` 或 `已检查-无风险`。
- `X`：状态为 `当前项有风险`。
- 标记与状态必须严格一致，不得留空或使用其他符号。

“关联详细项”列必须填写：

- 标记为 `V` 的行填写 `—`。
- 标记为 `X` 且存在已确认代码缺陷的行填写 `问题 #N`。
- 标记为 `X` 且属于测试、设计、配置、实测或确认材料缺口的行填写 `风险确认 #N`。
- 标记为 `X` 且命中专项强制提示条件的行必须关联 `风险确认 #N`，即使材料齐全也保留触发依据及已验证范围。
- 同一项同时存在代码缺陷和独立的证据缺口或专项强制提示时填写 `问题 #N；风险确认 #M`，不得重复展开同一代码根因。
- 每个 `X` 必须至少关联一个详细项；同一个根因可被多个汇总项关联，详细报告中不得重复展开相同根因。

专项强制提示由对应清单的触发条件决定，不等同于已确认代码缺陷，也不必然表示材料缺失。当前规则下，BMC 升级/系统内部文件变更，以及 IPMI 权限变更命中调用方，必须保留 `X` 和关联的风险提示；通用的证据补齐或风险关闭不能自动覆盖该要求。是否阻塞合入由项目门禁决定，不得仅因 `X` 虚构代码缺陷或缺失材料。

其中：

- “提交标题、Description、Tracker”行必须覆盖按模块提交、标题格式、Description 类型与内容及 Tracker；“测试步骤与测试结果”单独记录测试证据。
- “全仓符号冲突”行在涉及相关符号时，必须逐个列出标识符、搜索范围、定义/声明/引用命中位置、冲突分类和结论；多个标识符可在同一单元格内使用 `<br>` 分行。
- “Sensor 参数”行在新增或修改 Sensor 时，必须逐 Sensor 使用 `Sensor 名称：Disabled=...；No Reading=...；告警值=...；优先级/恢复=...；负值可能性=...；类型链=...；负值策略=...；散热策略=...；Health LED 映射=...；LED 恢复条件=...` 格式列出显示场景、负值处理、散热策略及 LED 依据；温度 Sensor 写明 thermal zone/PID/风扇曲线、阈值、动作、fail-safe 和测试，非温度 Sensor 写“不涉及（非温度 Sensor）”。Health LED 映射必须覆盖各种阈值/离散告警的级别、颜色/模式和并发优先级；无联动或无某类场景时写明依据。

无确认代码问题且存在风险确认项时，写“未发现确认代码问题，待确认风险见下文”；所有汇总项为 `V` 时，才写“未发现问题”。删除空的问题行，但保留已检查事项和证据限制。

## 确认代码问题

仅展开有代码证据支持的真实缺陷。相同根因只展开一次，但必须在“关联汇总项”中列出所有关联的 `X` 行。

### 问题 #1. `[严重级别]` 问题标题

**关联汇总项**：#N、#M

**问题点**：精确描述缺陷并引用新版本代码位置。

**风险/后果**：说明对安全、稳定性、长期运行、数据或兼容性的影响。

**修复建议**：给出可执行的修改方式；必要时提供最小代码片段。

**验证建议**：说明修复后应执行的测试或检查。

## 待确认风险与证据缺口

每个未由“确认代码问题”完全覆盖的 `X` 都必须在本节关联一个详细项；专项强制提示也必须在本节保留，不能仅由代码问题替代。此类项目不是已确认代码缺陷。普通证据缺口在材料补齐且相关风险关闭前不得标记为 `V`；专项强制提示在本次变更仍满足触发条件、且专项规则未调整时，材料齐全或普通风险关闭后仍须保留 `X`。

### 风险确认 #1. 风险标题

**事项类型**：证据缺口 / 专项强制提示；兼有两类时并列填写，分别说明缺失材料与强制提示依据。

**关联汇总项**：#N、#M

**代码/配置位置**：相关代码位置；无法定位时说明搜索范围和覆盖限制。

**待确认事项/提示依据**：证据缺口列出需要确认的设计、行为、测试或外部材料；专项强制提示列出触发条件、专项规则依据及已验证范围。

**风险/影响**：基于实际影响范围说明可能造成的功能回归、安全、散热、告警或兼容性影响；材料齐全且已验证的内容如实说明，不把强制提示写成已确认缺陷。

**需补充材料**：只列实际缺失的测试结果、测量数据、配置、确认邮件或其他证据；材料齐全时写明“无（已提供……）”，不得为保留 `X` 虚构材料缺口。

**关闭条件/标记限制**：证据缺口明确所需材料或验证结论，且关联汇总项的全部问题与风险关闭、未命中专项强制提示时，才可改为 `V`；专项强制提示写明当前必须保留 `X` 的依据。同一事项兼有两类时，补齐材料仅关闭证据缺口，不自动解除强制提示。

## 正向评价

仅在确有具体良好实践时输出，并说明其价值；没有则省略本节。
